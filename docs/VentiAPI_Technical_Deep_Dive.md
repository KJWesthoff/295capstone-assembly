# VentiAPI Technical Deep Dive

## 1. Architecture & System Design

VentiAPI employs a **microservices architecture** orchestrated via Docker Compose, designed for modularity and isolation. The system comprises the following core components:

### Core Services
-   **Web API (`scanner-service/web-api`)**: A Python FastAPI application serving as the central orchestrator. It manages scanner lifecycles, parses results, and exposes REST endpoints for the frontend.
-   **Cedar Mastra Backend (`cedar-mastra`)**: A Node.js/TypeScript service hosting the "Security Analyst" AI agent. It handles RAG (Retrieval Augmented Generation) operations, tool execution, and LLM interactions.
-   **PostgreSQL**: The primary persistence layer, utilizing the `pgvector` extension to serve as both a relational store for findings and a vector database for security intelligence embeddings.
-   **Redis**: Implements a job queue for background tasks and caching to ensure system responsiveness.
-   **Nginx**: Acts as a reverse proxy, handling SSL termination and routing traffic to the frontend and API services.

### Scanner Integration
The system integrates three distinct scanning engines, each running in isolated Docker containers:
1.  **VentiAPI Scanner**: A custom-built engine targeting specific API vulnerability patterns.
2.  **OWASP ZAP**: Used for DAST (Dynamic Application Security Testing) and OpenAPI-based scanning.
3.  **ProjectDiscovery Nuclei**: A template-based scanner for identifying misconfigurations and known vulnerabilities.

### Deduplication Logic
VentiAPI implements **hash-based deduplication** at the database level. Finding uniqueness is enforced using a cryptographic fingerprint generated by the SQL function `generate_finding_fingerprint`:
```sql
md5(CONCAT(p_rule, ':', p_endpoint, ':', p_method))
```
This ensures that identical findings—same rule, endpoint, and HTTP method—are not duplicated, even across multiple scan runs.

## 2. Artificial Intelligence & RAG Pipeline

VentiAPI's AI capabilities go beyond simple LLM wrapping, featuring a structured **Agentic Workflow** built on the Mastra framework.

### The Security Analyst Agent
The "Security Analyst" is an autonomous agent that follows a strict workflow:
1.  **Scan Analysis Workflow**: Automatically triggers upon scan completion. It preprocesses raw JSON scan results into a condensed textual summary (`scanContext`).
2.  **RAG Retrieval**:
    -   **Embedding Model**: Uses `mistral-embed` to generate vectors for security advisories and code examples.
    -   **Vector Database**: Queries the `code_examples` table in PostgreSQL using vector similarity (supported by `pgvector`).
    -   **Context Construction**: Retrieves relevant OWASP guidelines, CWE definitions, and verified code examples to build a `securityContext`.
3.  **Structured Generation**: The LLM (GPT-4o) processes the combined context to generate a report adhering to a strict `SecurityAnalysisSchema` (Zod schema), ensuring consistent, machine-readable outputs rather than unstructured text.

### Tools & Capabilities
The agent is equipped with specialized tools:
-   **`visualizeAttackPathTool`**: Generates Mermaid.js diagrams to visually depict vulnerability exploitation flows.
-   **`remediationPrioritizationTool`**: Calculates a dynamic priority score (P0-P3) based on severity, exploitability, and asset criticality.
-   **`getSecurityIntelligenceTool`**: Fetches real-time vulnerability data from the knowledge base.

## 3. Data Sources & Knowledge Base

The system's intelligence is derived from a multi-source knowledge base, actively maintained by ingestion scripts:

### Primary Sources
-   **GitHub Security Advisories**: Ingested via `ingest-github-advisories.ts`. This is the primary source for "verified code examples" (both vulnerable and fixed versions).
-   **NIST NVD**: Ingested via `ingest-nist-nvd.ts` for comprehensive CVE metadata.
-   **ExploitDB**: Ingested via `ingest-exploitdb.ts` to correlate findings with known active exploits.
-   **OWASP & CWE**: Foundation data for categorization and terminology.
-   **Breach History**: A dedicated `Data_Breach_Chronology_sample.db` provides historical context for real-world impact analysis.

### Self-Healing Data
The `ingest-github-advisories.ts` script includes a "background enrichment" mechanism. when a query fails to find sufficient local data, it triggers a fetch from the upstream API and automatically ingests the new findings, effectively "healing" gaps in the knowledge base over time.

## 4. Security & Engineering Practices

### Security Limitations
-   **Authentication**: The current `UserDB` implementation in `security.py` is a simplified, file-based store suitable for demonstration but not production.
-   **Scanning Scope**: The scanners are configured with strict resource limits (CPU, memory) and network isolation (`--security-opt no-new-privileges`) to prevent container breakout, though `host` network mode is used for localhost scanning, which carries some risk.
-   **Input Validation**: Strict validation is applied to all URLs and file uploads (`security.py`), blocking dangerous patterns (e.g., internal IP ranges, malicious YAML tags).

### Interactive UX
The frontend (Cedar) utilizes a "Spell" system for interactive components:
-   **`RadialMenuSpell`**: Context-sensitive actions on findings.
-   **`TooltipMenuSpell`**: Smart hovers for rapid information access.
-   **`QuestioningSpell`**: Guided workflows for remediation.

## 5. Key Differentiators

| Feature | Standard Implementations | VentiAPI Implementation |
| :--- | :--- | :--- |
| **Scanning** | Single engine (often ZAP or custom) | **Multi-Engine Orchestration** (ZAP + Nuclei + Custom) with unified deduplication. |
| **AI Analysis** | Generic "Chat with PDF" style RAG | **Agentic Workflow**: Structured, schema-enforced analysis with autonomous tool usage. |
| **Exploitation** | Static text description | **Visual Attack Paths**: Dynamic generation of Mermaid diagrams showing the exact attack flow. |
| **Remediation** | Generic advice | **Context-Aware Fixes**: RAG retrieves *verified* code examples matching the specific language/framework. |
| **Prioritization**| Static CVSS score | **Contextual Scoring**: Formula considering exploitability, fix availability, and asset criticality. |
